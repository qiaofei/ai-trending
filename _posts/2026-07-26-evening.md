今晚这批项目有个共同特征：都诞生于今年 2–3 月，经过约半年迭代后，抽象层次已经分化。早期 agent 项目普遍是"框架 + 一堆集成"的大杂烩，而现在能看到清晰的三层切分——**单体 agent 运行时**负责 loop、memory 与 provider 适配；**能力接入层**负责让 agent 触达外部数据源；**控制平面**负责多 agent 的调度、预算与审计。第三层是今年新长出来的，它出现说明"跑一个 agent"已经不是问题，"跑二十个还不失控"才是。另一个信号是版本节奏：这三个项目都有规律的 release 与明确的 breaking change 记录，不再是 push-to-main 的原型状态。

---

## 1. [HKUDS/nanobot](https://github.com/HKUDS/nanobot) — 把 agent 核心循环压到可读范围

**46,255 star · 创建于 2026-02-01 · Python · MIT · 最新版本 v0.1.5.post3（2026-04-29）**

**解决的问题**：主流 agent 框架为了覆盖全场景，把 tool 调度、memory、provider 适配层层包装，核心 loop 淹没在抽象里，出问题时无法定位。nanobot 明确对标 Claude Code / Codex 的形态，目标是"core agent loop 保持小且可读"，同时不牺牲 channel 接入、memory 与部署能力。

**技术架构**：四层平铺而非嵌套——Providers（约 20 家 LLM 后端，含 Anthropic、DeepSeek-V4、Kimi K2.6、MiniMax、Ollama、LM Studio）、Channels（Discord/Telegram/Slack/飞书/微信/Teams/Matrix/钉钉等十余个）、Tools & Skills、Memory。控制流是单一事件循环：消息进入后由 LLM 决策是否调用工具，memory 与 skill 按需拉取上下文，而不是前置塞满 prompt。

**关键实现**：其一，v0.1.5 引入两阶段 memory（"Dream"）与 token-based 上下文 auto-compact，session 以 JSON 本地落盘，配合 atomic session write 与 auto-repair 应对并发写入损坏；其二，长任务采用 virtual tool-call heartbeat 维持响应，跨 channel 共享统一 session；其三，MCP 支持把 resources 与 prompts 直接暴露成 tool，可挂多个 MCP server 并带自定义鉴权头与 SSE 流式；对外另提供 OpenAI 兼容 API 与 Python SDK facade。依赖上 v0.1.4.post6 起已用 `openai` + `anthropic` 官方 SDK 替掉 litellm，减少一层间接。

**演进情况**：2–4 月的 release 主线是生产硬化——shell 沙箱加固、secrets 管理、Windows 与 Python 3.14 支持、Office 文档读取、多 provider web search。4 月后主干仍在高频 push（今日仍有提交），但未再打 tag，说明处于下一个版本的积累期。

**取舍与局限**：845 个 open issue 对 46k star 的项目偏高，channel 覆盖广带来的维护面是真实代价（Telegram 高并发下的韧性问题曾专门修过）。WebUI 尚未随官方包发布，需源码 checkout 才能开发。Docker 与 systemd 部署要手工配置，无官方托管版本。auto-compact 的实际效果仍受底层 provider 上下文窗口约束。

**可借鉴**：把 provider/channel/tool/memory 做成四个平级可替换层、而不是继承树，是这个项目最值得抄的结构决策；atomic session write + auto-repair 这种"本地 JSON 也要当数据库对待"的保守做法，对任何长跑 agent 都适用。

## 2. [Panniantong/Agent-Reach](https://github.com/Panniantong/Agent-Reach) — 脚手架而非框架的能力接入层

**60,949 star · 创建于 2026-02-24 · Python · MIT · 最新版本 v1.5.0（2026-06-11）**

**解决的问题**：agent 要读 Twitter、Reddit、YouTube、小红书、B站这些平台，现状是付费 API、登录墙、403 封锁、脏数据各占一摊。自己写爬虫的维护成本会在几周内吃掉全部收益。

**技术架构**：作者把定位写得很明白——"脚手架（scaffolding），不是框架"。它本身几乎不含抓取逻辑，而是一个可插拔编排层：探测并安装上游工具 → 以 SKILL.md 形式向 agent 注册能力 → agent 直接调用底层命令，中间不加 wrapper。channel 是一等公民且互相独立：Web 走 Jina Reader，视频走 yt-dlp（覆盖 1800+ 站点），Twitter/Reddit/小红书/B站各走对应 CLI，语义搜索经 mcporter 挂 Exa MCP，RSS 用 feedparser。仓库体积只有 1.7 MB，印证了这个"不自己造轮子"的定位。

**关键实现**：其一，不做 wrapper 是有代价也有收益的关键取舍——上游 yt-dlp 一更新即刻生效，无需本项目跟版；其二，v1.5.0 把架构升级为"capability layer"，为同一平台配置多后端并做真实健康检查，自动路由到当前最稳定的访问路径，这是从"工具集合"到"带故障转移的接入层"的质变；其三，凭据统一存 `~/.agent-reach/config.yaml` 且强制 600 权限，不外传；安装侧提供 `--safe` 与 `--dry-run`，`agent-reach doctor` 支持 JSON 输出便于纳入自动化巡检。

**演进情况**：版本节奏密集且方向明确。v1.4.0（3 月）做上游大迁移换掉不稳定后端；v1.4.2（6 月）主动砍掉无人维护的 TikTok、微博、微信 channel 并接入 Whisper 转写——**做减法**在这类项目里是健康信号；v1.5.0 引入多后端路由。趋势是从广度转向可靠性。

**取舍与局限**：README 不提供任何 benchmark（延迟、成功率、吞吐全无），可靠性只能靠 doctor 自测。Cookie 登录类平台有实打实的封号风险，官方建议用小号。海外服务器跑 B站需住宅代理。无内建重试与限流逻辑，每次调用无状态。上游任何一处改版都需人工跟进——这是"不做 wrapper"的账单。

**可借鉴**：SKILL.md 作为 agent 与工具之间的注册契约，比写 MCP server 轻得多；以及"健康检查驱动的多后端路由"这个模式，对任何依赖不可靠第三方的系统都通用。

## 3. [paperclipai/paperclip](https://github.com/paperclipai/paperclip) — 把 agent 当员工管的控制平面

**74,769 star · 创建于 2026-03-02 · TypeScript · MIT · 最新版本 v2026.722.0（2026-07-22）**

**解决的问题**：开着二十个 agent 会话，分不清哪个在做什么，重启即丢上下文，成本无人管、执行无审计。paperclip 的自我定位是"full control plane, not a wrapper"——治理层，不是又一个 agent 框架。

**技术架构**：Node.js 服务 + React UI + PostgreSQL（本地内嵌，生产接外部实例），核心是把公司组织结构当数据模型：Identity & Access、Org Chart（角色、汇报线、权限）、Issue-based 工作系统、Heartbeat 执行、审批与治理、预算与成本、Routines（cron）、Plugins、加密 Secrets、不可变 Activity 日志。所有实体 company-scoped，单部署可跑多组织且数据与审计链隔离。

**关键实现**：其一，执行模型是 **heartbeat 而非常驻**——agent 按调度醒来、领任务、行动，session 落库因而可跨重启恢复；任务采用数据库锁做 atomic checkout，从机制上杜绝重复领取。其二，预算是硬约束而非告警：按 company/agent/project/goal/issue/provider/model 多维计账，超限自动暂停 agent 并取消排队任务。其三，任务携带完整 goal ancestry，agent 拿到的不只是标题还有"为什么"；配合 runtime skill injection，无需重训即可让 agent 学会本地工作流。接入面很宽——OpenClaw、Claude Code、Codex、Cursor、bash CLI、HTTP webhook 皆可，判据只有一条："If it can receive a heartbeat, it's hired."；工具访问经 MCP 受控，可选 OpenTelemetry 导出。

**演进情况**：master 已 3,222 次提交，采用日期版本号（v2026.722.0，7 月 22 日），发布节奏接近持续交付。近期能力偏向可移植性与安全恢复：org/agent/skill 模板可导出导入并自动擦除 secret、处理命名冲突，配置变更带版本可回滚。

**取舍与局限**：作者自己划了三条界——不是 chatbot、不是拖拽式 workflow builder、单 agent 场景不必用。atomic checkout 与预算校验带来额外延迟，架构面向调度型 heartbeat，不适合亚秒级连续执行。强依赖 PostgreSQL，库没了 agent 状态就没了。4,953 个 open issue 说明高速迭代下的稳定性仍在追赶。

**可借鉴**："预算超限即硬停"和"每个变更可追溯到具体 actor"这两条，是多 agent 系统从玩具走向生产的分水岭；用 issue + goal ancestry 传递上下文，比塞长 prompt 更可控也更省 token。
