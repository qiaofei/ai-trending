本周的信号集中在 Agent 架构的**分化**上。Strix 走的是加法路线——多个专门化 agent 在图上并行协作；Superpowers 走的是减法路线——不增加 agent 数量，而是用强制方法论约束单 agent 的行为边界。两者针对的是同一个问题的不同面：前者解决能力不足，后者解决流程失控。第三个值得注意的是 Graphify，它在代码理解这件事上明确拒绝了当前 embedding + 向量召回的主流路线，改用纯符号图谱，是一次有分量的反向论证。

## 1. usestrix/strix

[usestrix/strix](https://github.com/usestrix/strix) · 44,339 ★ · Python · Apache-2.0 · 创建于 2025-08 · 最近 push 2026-07-26

**解决的问题**：自动化渗透测试工具的老毛病是误报率高——扫描器报一堆「可能存在」，人工复核的成本比扫描本身还贵。Strix 的目标是只输出**带可复现 PoC 的确认漏洞**。

**技术架构**：核心是 "Graph of Agents" 模式。recon、exploitation、post-exploitation 各自是专门化 agent，在图结构上并行执行并共享发现。关键设计在于 agent 之间能**链式组合漏洞**——A 找到的信息泄露作为输入喂给 B 做权限提升，这是单 agent loop 结构上做不到的。

**关键实现**：

- LLM 层用 **LiteLLM** 做 provider 抽象，支持 GPT-5.4 / Claude Sonnet 4.6 / Gemini 3 Pro / Bedrock / Vertex，也可接本地模型；有 `reasoning effort` 参数控制单次任务的算力投入，分标准与 quick-scan 两档
- 沙箱基于 **Docker**，首次运行自动拉取镜像。容器内集成 Caido（HTTP 拦截代理）、Playwright（浏览器自动化，测客户端漏洞）、Nuclei 模板库、Python exploit 沙箱与交互式 shell
- 输出附 CVSS 评分、OWASP 分类与复现步骤，而非单纯的告警条目

**取舍与局限**：Docker 是硬依赖。CI 场景下需要 `fetch-depth: 0`，否则 diff-scope 解析不准。工具链集成度高的代价是依赖面很宽，容器镜像不小。有企业版在售，说明主线是按生产可用维护的。

**可借鉴**：「专门化 agent + 共享发现图」不限于安全领域。任何多阶段、且后阶段依赖前阶段产出的自动化流程，都可以套这个结构——比顺序执行的 pipeline 更能利用中间结果。

## 2. Graphify-Labs/graphify

[Graphify-Labs/graphify](https://github.com/Graphify-Labs/graphify) · 96,175 ★ · Python · MIT · 最近 push 2026-07-26

**解决的问题**：大型代码库的 AI 辅助检索目前基本靠 embedding + 向量召回，但代码的语义关系（谁调用谁、改这里会影响哪里）本质是**结构性**的，向量相似度捕捉不到。

**技术架构**：用 **tree-sitter 做 AST 抽取**，覆盖 36 种语法，包括 Salesforce Apex、Terraform/HCL 这类 DSL。构建内存知识图谱，序列化为 `graph.json`。查询走**子图抽取**而非全文检索，支持最短路径分析和按度数排序识别「god node」（高耦合中心节点）。社区划分用 **Leiden 算法**聚类。

**关键实现**：

- **代码抽取 100% 本地、零 API 调用**。LLM 只用于非代码媒体（文档、PDF、图片）的语义抽取，后端可接 Anthropic / Gemini / OpenAI / DeepSeek / 本地 Ollama（可完全离线）
- 集成面很宽：MCP stdio + HTTP server、Claude Code / Cursor / Codex / Gemini CLI 原生 skill、git post-commit hook 自动重建索引
- 可导出 GraphML / Neo4j Cypher / Mermaid；`graphify prs --triage` 做 PR 影响面分析

**演进情况**：项目自我描述里明确写了 "no vector store"，把「不用向量库」当作卖点而非妥协——这个定位比早期版本更鲜明，说明它在有意识地占据 RAG 路线的对立面。

**取舍与局限**：图大小上限 512 MiB（可通过环境变量调整），HTML 可视化超过约 5000 节点后交互明显变卡。**没有 embedding 意味着模糊语义查询能力弱**——问「哪里处理了用户认证」这类问题不如向量检索。这是有意的取舍，换来的是确定性、可解释性和零推理成本。

**可借鉴**：「符号图谱做结构、LLM 只补语义空缺」这个分工，比全量 embedding 更省钱也更可审计。做代码工具的可以直接抄这个边界划分。

## 3. obra/superpowers

[obra/superpowers](https://github.com/obra/superpowers) · 261,399 ★ · Shell · MIT · 创建于 2025-10 · 最近 push 2026-07-24

**解决的问题**：coding agent 的失败模式往往不是「不会写代码」，而是**流程失控**——跳过设计直接动手、不写测试、一次改动铺太大导致 review 无从下手。

**技术架构**：它不是框架，是**强制工作流层**。skill 是可组合的方法论模块，放在 `/skills` 下，由 agent 在任何任务前自动检查并触发。跨平台通过 `.claude-plugin` / `.codex-plugin` / `.agents/plugins` 做 harness-specific wrapper，靠 session-start hook 激活。**不走 MCP**。

**关键实现**：

- 强制七阶段：brainstorming → git worktree 隔离 → 计划拆到 **2–5 分钟粒度** → subagent 执行 → TDD（RED-GREEN-REFACTOR）→ 按严重度阻断的 code review → 分支收尾
- **每个任务派发全新 subagent**，两阶段 review（spec 合规 + 代码质量）；`dispatching-parallel-agents` 支持并发派发
- skill 本身用外部 eval harness（`superpowers-evals`）做行为测试——等于给 prompt 写单元测试，这在同类项目里很少见

**演进情况**：已发布到 v6.1.1，10 个 release，628 次提交。官方明确表示**基本不接受新 skill 的 PR**，扩展靠 fork——这是有意收窄的治理策略，保证跨 harness 兼容性，代价是社区贡献路径受限。

**取舍与局限**：强制流程对小改动是明显的过度工程，改一行也要走完整套。有可选遥测（仅版本号，`DISABLE_TELEMETRY` 可关）。

**可借鉴**：「任务拆到 2–5 分钟 + 每任务派发全新 subagent」是对抗 context 污染的实用手段。给 prompt 建 eval harness 更是值得直接搬进自己工程流程的做法。
