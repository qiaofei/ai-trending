这一轮从 `llm-inference`、`vector-database`、`model-serving` 三个 topic 里挑出的项目，共同点比表面差异更明显：**它们都在做资源置换**——把 GPU 显存、SSD 容量、CPU 拷贝这类紧俏资源，换成别处相对便宜的开销。Dynamo 用 KV 分层卸载和缓存感知路由换掉重复 prefill；LEANN 用查询时重算换掉 97% 的向量存储；OpenLake 用完成式 I/O 与纠删码，试图把 CPU 从数据通路上摘掉。分歧点在成熟度：一个是 v1.1.1 的生产系统，一个有 MLSys 论文背书，一个连核心卖点都还没实现。

## 1. [ai-dynamo/dynamo](https://github.com/ai-dynamo/dynamo) — 7,589 star · Rust · Apache-2.0 · 最近 push 2026-07-27

**解决的问题**：单机推理引擎（vLLM/SGLang/TensorRT-LLM）已经把单卡吃干榨净，但跨节点集群调度仍是空白——请求被随机打到 worker，导致同一 prefix 反复做 prefill；prefill 与 decode 计算特征迥异却被绑在同一组 GPU 上按同一比例扩缩。

**技术架构**：Dynamo 不替换引擎，而是叠在其上做编排层，拆成四个组件：Frontend（OpenAI 兼容网关）、Router（KV 感知路由）、Planner（SLA 驱动的自动扩缩）、Workers（引擎实例），外加 KV Block Manager（KVBM）负责缓存分层。控制流是「请求进入 → Router 评估 KV 重叠度与 worker 负载 → 分派到 prefill 池或 decode 池 → KVBM 协调缓存放置 → Planner 依 TTFT/ITL 调整池大小」。

**关键实现**：

- **Disaggregated serving**：prefill 与 decode 拆成两组可独立扩缩的 GPU 池，各自按计算密集 / 访存密集的特征选硬件配比。
- **KVBM 四级卸载**：GPU VRAM → host CPU 内存 → SSD → 远端对象存储（S3/Azure Blob），把有效上下文长度撑到超出显存容量。KV 感知路由官方数据是 Qwen3-Coder 480B 上 TTFT 快 2×。
- **ModelExpress** 权重流式加载走 NIXL/NVLink 做 GPU 到 GPU 传输，DeepSeek-V3 冷启动快 7×；Planner 配合 AIConfigurator 可在数秒内模拟一万余种部署配置，宣称 SLA 违约减少 80%、TCO 降 5%。
- 代码 Rust 约 54%、Python 30%、Go 13%——数据面在 Rust，扩展面留给 Python bindings。

**取舍与局限**：编排层意味着多一跳，小规模单机部署纯属负担；KV 感知路由需要 NATS 做 prefix 协调，Slurm 场景还要 etcd，依赖不算轻。构建依赖 CUDA、HWLOC、protobuf、Rust toolchain，绑定 NVIDIA 生态较深。已发布 v1.1.1（2026-05-09），5000+ commit、70+ 贡献者，属于可上生产的成熟度。

**可借鉴**：「路由决策应当读取缓存状态」这一条对任何有状态服务都成立——把 prefix cache 命中率当成负载均衡的一等输入，而不是等 LRU 自己碰运气；以及把 SLA 指标（TTFT、token 间延迟）而非 CPU 利用率作为扩缩容信号。

## 2. [StarTrail-org/LEANN](https://github.com/StarTrail-org/LEANN) — 12,735 star · Python/C++ · MIT · 最近 push 2026-07-24

**解决的问题**：向量库把所有 embedding 永久落盘，60M chunk 的 Wikipedia 索引要 201 GB。在个人设备上做私有 RAG，这个体量直接排除了本地部署的可能。

**技术架构**：核心思路是**不存 embedding，只存图**。索引阶段构建近邻图并做剪枝，查询时沿图遍历，仅对实际访问到的节点现算向量。数据流为「摄入 → chunking → 图构建与剪枝 → 查询时按需重算 → 检索结果」，图以 CSR（压缩稀疏行）格式存储。后端双选：HNSW（默认，存储节省最大）与 DiskANN（PQ 引导遍历 + 实时重排，搜索性能更好）。

**关键实现**：

- **High-degree preserving pruning**：剪掉冗余边但保留高度数的 hub 节点，用少量关键连通性换掉大部分图存储。
- **两级搜索 + 动态批处理**：遍历时优先展开高潜力节点以压缩需重算的节点总数，再把这批 embedding 计算合并成大 batch 喂给 GPU，用吞吐摊掉重算延迟。
- **实测存储对比**：Wiki 60M chunk 201 GB → 6 GB；聊天记录 400K 条 1.8 GB → 64 MB；邮件 780K 条 2.4 GB → 79 MB，节省率稳定在 95–97%。
- 工程侧 `leann build/search/ask/watch` 四个命令，`watch` 用 Merkle tree 做文件变更检测增量更新；接入面覆盖 Apple Mail、Chrome 历史、微信、iMessage 以及 Slack/Twitter（走 MCP）。

**取舍与局限**：拿存储换算力，代价是查询延迟——重算无法完全被批处理抹平，且实际上要求有 GPU，纯 CPU 模式明显慢。索引构建成本也高于普通向量库。当前 v0.3.7，出自 Berkeley Sky Computing Lab，有论文（arXiv:2506.08276，MLSys 2026）支撑，但仍属研究转工程阶段。

**可借鉴**：「存储 vs 计算」的置换点在硬件代际变化下会移动——当嵌入模型足够小、GPU 足够快，重算就可能比 I/O 更便宜。这个判断可以直接套用到特征存储、缓存物化视图等场景：先量化一次单位重算成本，再决定要不要真的把结果存下来。

## 3. [openlake-project/openlake](https://github.com/openlake-project/openlake) — 2,288 star · Rust · Apache-2.0 · 最近 push 2026-07-26

**解决的问题**：训练和推理的数据通路上，对象存储普遍要过 host CPU、page cache 暂存、多次用户态拷贝，CPU 成了 NVMe 到 GPU 之间的瓶颈。OpenLake 的目标是把 CPU 从关键路径上摘掉。

**技术架构**：四个 crate 分层——`phenomenal_io`（io_uring 本地 I/O、`xl.meta` 元数据编解码）、`phenomenal_storage`（纠删码、集群拓扑、SipHash 路由、dsync 式分布式锁）、`phenomenal_server`（S3 HTTP 前端、SigV4 鉴权、节点间 RPC）、`phenomenal_cli`（诊断与微基准）。当前数据流是「S3 client → cyper-axum(compio/io_uring) → SigV4 → SipHash 路由到 erasure set → 本地盘或 HTTP/2+mTLS 打到对端 → xl.meta + Reed-Solomon 分片」。目标形态则是 `NVMe → io_uring → NIC → RDMA/RoCEv2 → GPUDirect → GPU VRAM`。

**关键实现**：

- **运行时选 compio 而非 tokio**：completion-based 而非 readiness-based，每核一个 pinned runtime、不做 work stealing，配 `SO_REUSEPORT`，HTTP 前端与存储引擎同线程落位，消除跨线程交接。
- **格式兼容 MinIO 的 `xl.meta` v1.x**：≤128 KiB 的对象直接内联进元数据，更大的走 Reed-Solomon 分片；纠删码用 `reed-solomon-simd` 的 FFT 算法，自动探测 SSSE3/AVX2/NEON，并按 stripe 流式编码——峰值内存是一个 stripe 而非整个对象。
- **集群**：启动时把扁平磁盘池切成定宽 erasure set，每个 (bucket, key) 经 SipHash 确定性落到唯一一组，写全读任意达成 quorum，S3 wire 兼容 aws-cli / boto3 / mc。

**取舍与局限**：需要说清楚——**最核心的 GPUDirect Storage、RDMA、CPU 旁路数据通路都还没实现**，仓库自述处于早期阶段，README 也没有任何公开 benchmark 数字，只有 CLI 里的 `phenomenal bench`。定宽 erasure set 意味着扩容不灵活；compio 生态远小于 tokio，出问题时可查资料有限；io_uring 决定了实质只支持 Linux。

**可借鉴**：thread-per-core + completion I/O + 不做 work stealing 这套组合，在存储和网络中间件里正在成为新的默认解；以及「兼容既有格式（`xl.meta`）来换取整个客户端生态」是新存储项目冷启动的实用路径——协议兼容比性能宣称更早决定能不能被用起来。
