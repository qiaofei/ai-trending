过去 30 天新建仓库的 star 榜上，最热的是 agent harness（xai-org/grok-build 两周 23k star），但真正有工程含量的增量集中在 MoE 基础设施：单机把 700B 级模型跑起来的内存分层、多卡训练里路由倾斜带来的 EP 通信塌陷、以及 agentic RL 所需的海量沙箱环境。这三件事恰好是同一条链路上的三个瓶颈，本期各挑一个代表项目拆解。

---

### 1. [JustVugg/colibri](https://github.com/JustVugg/colibri) — 20,182 star · 创建于 2026-07-01 · C · Apache-2.0

**问题**：GLM-5.2 是 744B 总参、约 40B 激活的 MoE，int4 权重仍有约 372 GB，消费级机器装不下。

**架构**：把 VRAM / RAM / SSD 当成一个统一的托管内存层级。dense 部分（attention、shared expert、embedding，约 17B）int4 常驻 RAM 约 9.9 GB；19,456 个 routed expert（每个 int4 约 19 MB）留在磁盘，按需流式加载，配 per-layer LRU + 学习出来的 pinned hot-store + 可选 VRAM 层。作者称之为「JIT，但对象是权重」。关键前提是每 token 只有约 11 GB 权重发生变化。

**关键实现**：① router lookahead 线程（`PILOT=1`）提前一层预测下一层要用的 expert，实测一层前瞻的路由可预测性 71.6%，预取与计算重叠（`PIPE=1` 有界异步 I/O 池）；② MLA 压缩 KV 每 token 576 float（对比 32,768，57×），并持久化到 `.coli_kv`，重开对话零 re-prefill 且与未中断会话逐字节一致；③ 原生 MTP head 做投机解码，命中时 2.2–2.8 token/forward，但 MTP head 必须 int8——int4 会让接受率塌到 0–4%。整个引擎是单个 C 文件 `c/glm.c` 加少量头文件，运行时无 BLAS、无 Python、无 GPU 依赖。

**取舍与局限**：只支持 GLM-5.2 一个模型；速度对「快内存有多少」极度敏感——6× RTX 5090 全驻留 5.8–6.8 tok/s、128 GB CPU-only 约 1.8 tok/s、25 GB 冷启动只有 0.05–0.1 tok/s，后者是「能跑」而非「可用」。O_DIRECT 旁路收益依盘而异，QLC / 无 DRAM / 虚拟化磁盘上可能为负。

**可借鉴**：把稀疏激活重新表述成缓存问题——先量化「每 token 真正变化多少字节」，再决定分层策略；以及 KV cache 持久化换 prefill 这一招，对长会话服务同样成立。

### 2. [MoonshotAI/MoonEP](https://github.com/MoonshotAI/MoonEP) — 416 star · 创建于 2026-07-24 · Python/CUDA · MIT

**问题**：MoE 训练里 router 输出天然倾斜，expert parallelism 的 all-to-all 就被最热的那个 rank 拖住，DeepEP 一类实现的 iteration time 随 maxvio（`max_e(T_e/T̄) - 1`）单调上升，极端倾斜下还会 OOM。

**架构**：dynamic redundant experts。每步根据当前路由在线规划、少量复制热点 expert，并在计算前预取其权重；反向时把冗余副本的梯度 reduce 回 home rank。规划本身由一个专用 GPU kernel 完成，开销可忽略。结果是每个 rank 恒定收到 `S×K` 个 token，maxvio 被设计成 0。

**关键实现**：① 权重按 `[E+B, H, H']` 单块连续对称内存张量组织，`[0,E)` 是各 rank 本地 expert，`[E,E+B)` 是预取槽，训练默认 `B = E/R`；形状静态已知，因此没有内存碎片和 per-layer host 同步。② 零拷贝 dispatch：token 直接经 NVSHMEM 写到远端 rank 的 expert 分组位置，返回 buffer view 供计算，permute/unpermute 融合。③ API 面很小：`dispatch / combine / prefetch_weight / reduce_grad`，框架侧只需提供连续对称内存权重和 planner 产出的 `cu_seqlens`。H20 + EP=8 实测：通信时间随 maxvio 增长几乎持平，端到端 iteration time 在各倾斜档位保持平坦。

**取舍与局限**：强依赖 NVLink + 对称内存（NVSHMEM），非 NVLink 拓扑无从谈起；冗余副本要额外显存（B 个槽位）；论文与代码都很新（Zhenwu PPU 支持仍在 review），缺第三方复现。

**可借鉴**：与其在 router 端加 aux loss 硬压平衡（伤模型质量），不如在系统层用「复制热点 + 静态形状」把不平衡吸收掉——负载均衡从损失函数问题变回调度问题。

### 3. [kvcache-ai/AgentENV](https://github.com/kvcache-ai/AgentENV) — 637 star · 创建于 2026-07-23 · Rust · MIT

**问题**：agentic RL 需要同时挂起成千上万个隔离环境，容器方案里「空闲环境」并不便宜，冷启动和镜像分发也拖慢 rollout。项目自述用于支撑 Kimi K3 的训练。

**架构**：以 Firecracker microVM 为隔离原语跨多机部署；镜像用 OCI 格式经 overlaybd 按需加载，本地盘退化为有界缓存（热数据保留、冷数据淘汰），因此镜像总量可以超过单机磁盘且无需逐机预热。内存与文件系统快照落 S3 兼容对象存储或共享分布式文件系统。

**关键实现**：① 生命周期数字是核心卖点——boot/resume < 50 ms，pause < 100 ms，重度写盘下的快照仍 < 100 ms；② memory ballooning 把可回收的 guest 内存还给宿主，环境运行越久越分化时仍能维持高超卖比，这正是「空闲环境便宜」的来源；③ 运行中的环境可 fork 成多个独立沙箱，直接对应树搜索式 rollout；④ 对外暴露 E2B 兼容 HTTP API，现有 E2B Python/TS SDK 改个 endpoint 即可复用，`aenv` CLI 管模板与沙箱生命周期。

**取舍与局限**：要求 Linux 6.8+、`/dev/kvm`、安装脚本只覆盖 Ubuntu 24.04，等于绑死裸金属；依赖链偏重（Firecracker + overlaybd + 分布式存储）；README 未给吞吐/并发密度的对比数据，50 ms 之类的数字暂无第三方验证。

**可借鉴**：把「沙箱」的成本模型从 CPU 时间改写成内存超卖 + 快照延迟，是 agent 基础设施的通用视角；以及兼容既有 E2B API 而非另立协议，这种「接口寄生」策略显著降低了迁移成本。
