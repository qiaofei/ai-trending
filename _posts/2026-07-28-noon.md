本期三个项目分处推理栈的三层——GPU attention kernel、端侧 ARM 运行时、嵌入式向量索引——但技术路线撞到了同一个点：先做随机旋转把方差摊平到各维，再压到 INT4/FP4 甚至更低。这是 QuaRot/Hadamard 那一系思路从 LLM 权重量化外溢到向量检索的直接证据。分歧则在如何对付硬件异构：FlashInfer 选 JIT 加多后端运行时分派，Cactus 选手写死 ARM SIMD kernel，Zvec 干脆退回进程内、不碰分布式。

---

### 1. [flashinfer-ai/flashinfer](https://github.com/flashinfer-ai/flashinfer) — 6,049 star · Python/CUDA · Apache-2.0 · 最近 push 2026-07-28

**问题**：LLM serving 的 attention 不是一个 kernel，而是一族——prefill / decode / append、paged 与 ragged KV、MLA、block-sparse、mixed batching 各有最优实现，且最优解随 SM 架构（7.5 到 12.1）漂移。每个推理引擎各写一套是重复劳动，写不全就留性能坑。

**架构**：定位为 serving 引擎下面的 kernel 层，不做调度、不管请求。内部按算子族划分：attention（含 cascade attention 处理层级化 KV、POD-Attention 处理混合 batch）、GEMM（BF16 / FP8 per-tensor 与 groupwise / NVFP4 与 MXFP4）、MoE 融合算子（含 FP8/FP4 专家权重与多种 routing）、sampling（sorting-free top-K/top-P/min-P）、以及 RoPE、RMSNorm、fused activation。每族下挂多个后端实现——FlashAttention-2/3、cuDNN、CUTLASS、TensorRT-LLM——运行时按硬件能力自动选。

**关键实现**：① 后端分派与 JIT 组合：既能按 SM 版本挑预编译 cubin，也能 JIT 生成带自定义参数的 attention 变体，分发拆成 `flashinfer-python`（按需编译）、`flashinfer-cubin`（全架构预编译）、`flashinfer-jit-cache`（按 CUDA 版本预建）三个包；② sorting-free 采样把 top-K/top-P 从排序改成免排序实现，去掉 decode 尾部的同步点；③ 已是 vLLM、SGLang、TensorRT-LLM、TGI、MLC-LLM、LightLLM、lorax、ScaleLLM 的公共依赖，事实标准地位比 star 数体现的更高。

**取舍与局限**：README 明说「并非所有特性在所有 compute capability 上都支持」，跨代移植要自行验证；865 个 open issue 说明覆盖面换来了维护面。CUDA 12.6/12.8/13.0/13.1 绑定较紧，非 NVIDIA 硬件无路可走。版本仍在 0.6.x（v0.6.13rc1，2026-06），API 未冻结。

**可借鉴**：把「一个算子」拆成「算子族 × 后端矩阵 + 运行时分派」，是硬件代际快速迭代下唯一可维护的形态；以及三段式打包（源码 JIT / 预编译二进制 / 预建缓存）值得任何有编译期负担的库抄。

### 2. [cactus-compute/cactus](https://github.com/cactus-compute/cactus) — 5,542 star · C++ · Other（见 LICENSE）· 最近 push 2026-07-28

**问题**：手机和可穿戴设备上跑多模态模型，瓶颈不是算力而是 RAM 和内存带宽。通用引擎把权重反复拷贝，1–2B 模型动辄吃掉 1 GB 以上常驻内存，在中低端 Android 上直接不可用。

**架构**：五层自下而上——Cactus Kernels（ARM NEON SIMD 手写 matmul / attention / convolution）、Cactus Quants（rotation-and-codebook 量化，4-bit 到 1-bit）、Cactus Graph（零拷贝计算图，张量通过 mmap 直接映射权重文件，不做 staging copy）、Cactus Engine（OpenAI 兼容的 text/speech/vision 接口）、Cactus Transpiler（把 PyTorch 模型转成自有 CQ 二进制格式）。绑定覆盖 Swift、Kotlin、Flutter、React Native、Rust、Python。

**关键实现**：① 零拷贝 mmap 是 RAM 数字的来源：Mac M4 Pro 上 LFM 1.2B INT4 常驻仅 76 MB，iPhone 17 Pro 108 MB，官方对比口径是「比其他引擎低 10 倍」；② 量化侧做旋转加码本而非朴素均匀量化，README 称 4-bit 可对齐 f16 质量；③ 实测 INT4 纯 CPU：M4 Pro prefill 582 / decode 100 tps，iPhone 17 Pro 327/48，Galaxy S25 Ultra 255/37，Pixel 6a 70/15；Apple Neural Engine 与 Qualcomm Hexagon 在部分机型上可用；④ 内置按置信度的云端 fallback 路由，端侧不确定时转发上云。

**取舍与局限**：模型面窄——LLM 集中在 0.6–2.6B（Gemma 3/4、Qwen、LFM、Youtu-LLM），语音靠 Moonshine/Whisper/Parakeet；必须经 transpiler 转成 CQ 格式，无法直接吃 GGUF，生态迁移成本实打实。低端 Android 断崖明显（Galaxy A17 约 32 tps，RAM 回到 1–1.5 GB 档）。部分 Android 旗舰缺 NPU benchmark，Whisper-large-v3 无 NPU 支持。License 标为 NOASSERTION，商用前需自行确认。

**可借鉴**：端侧优化的第一性问题是「权重被拷贝了几次」而不是「kernel 快不快」；把量化格式、内存布局、kernel 三者协同设计（而非拿现成格式套现成 kernel），才是 10× RAM 差距的来源。

### 3. [alibaba/zvec](https://github.com/alibaba/zvec) — 15,291 star · C++ · Apache-2.0 · 最近 push 2026-07-28

**问题**：多数向量检索场景数据量在千万级以内，却被迫部署一套独立的向量数据库服务，付出网络往返、运维和一致性协调三重成本。SQLite 之于 OLTP 的位置，向量侧长期缺位。

**架构**：进程内嵌入式库，无 server、无网络层，「代码跑在哪它就跑在哪」——notebook、服务进程、CLI、边缘设备。存储层用 WAL 保证进程崩溃或断电不丢数据；并发模型是多进程共享读、写入单进程独占，用放弃并发写换掉分布式协调。索引侧提供 HNSW、HNSW-RaBitQ、Flat 与 sparse index 四类，dense 与 sparse embedding 并存。

**关键实现**：① v0.6.0 引入随机旋转量化做 INT8/INT4 压缩，机制与 Cactus 的旋转量化同源——把方差均匀摊到各维再压比特，官方称显著提升 recall；② 内建全文检索不是附属品：Unicode 分词、UTF-8/ASCII folding、Snowball 词干还原覆盖 34+ 语言，可与向量相似度和结构化过滤在单条查询里融合（hybrid query）；③ v0.6.0 的 block-max skip 让 FTS 合取查询快 22–38%；group-by search 支持按组取 top-K 而非全局 top-K，做去重召回很实用；④ SDK 覆盖 Python 3.10–3.14、Node.js、Go、Rust、Dart/Flutter，平台含 Linux x86_64/ARM64、macOS ARM64、Windows x86_64。

**取舍与局限**：写入单进程独占，高并发写入场景不适用；无内建分片与副本，容量上限受单机约束。创建于 2025-12，v0.6.0 阶段 API 仍可能变动。「billions of vectors in milliseconds」的宣传口径与嵌入式定位存在张力，具体数字需按自己数据集复测。宣称在阿里集团内部经过验证，但外部可复现的第三方 benchmark 有限。

**可借鉴**：先问「这个系统真的需要分布式吗」——放弃并发写就能砍掉整个协调层，是被低估的架构杠杆；以及 hybrid search 应该在索引层原生融合，而不是在应用层做两次查询再手工 RRF。
