过去 30 天的新建仓库里，热度最集中的三条线索都指向同一个工程命题：**把模型能力从「够不够大」拉回到「跑得起、管得住」**。第一条是推理侧的内存层级化——把 MoE 的路由专家当作按需调度的数据而非常驻权重，用 NVMe 换 RAM；第二条是 coding agent harness 的官方化，xAI 直接开源了自家 TUI agent 的全套 crate；第三条是本地优先的桌面 agent 与工具接入层（openworker、open-connector 等）开始收敛出「审批门 + 凭据边界」这套安全范式。以下三个项目均为最近一个月内新建，且 `pushed_at` 都在 48 小时内，处于高频迭代期。

## 1. [JustVugg/colibri](https://github.com/JustVugg/colibri) — 19,643 star · 创建于 2026-07-01 · C · Apache-2.0

**解决的问题**：GLM-5.2 这类 744B 参数的 MoE 模型，int4 量化后权重仍有约 380 GB，常规做法要么整机堆内存要么多卡集群。colibri 的主张是：MoE 每个 token 只激活极小一部分专家，把全部专家常驻内存本身就是浪费。

**技术架构**：把 VRAM / RAM / NVMe 当成**一套统一管理的内存层级**。dense 部分（attention、shared experts、embeddings，约 17B 参数）以 int4 常驻 RAM，占约 9.9 GB；75 个 MoE 层 × 256 个路由专家 + MTP head，共 19,456 个专家（int4 下每个约 19 MB、合计约 370 GB）留在磁盘，由 router 判定后按需 stage 进来。作者称之为「JIT，但针对权重」——参数不是要持有的状态，而是要在正确时刻搬到正确层级的数据。

**关键实现**：

- **调度五步**：路由选择 → union 去重（批量位置对同一专家只读一次）→ 层级放置 → I/O 与计算 overlap → router 学习并更新缓存。每层维护 LRU，配合学习出的 hot-store pinning。
- **预取靠可预测性**：实测「提前一层预测路由的准确率为 71.6%」，这是 lookahead prefetch 能成立的前提。支持双 SSD 各放一份完整模型副本并行读，用带宽换延迟。
- **KV cache 用 MLA 压缩**：每 token 存 576 个 float 而非 32,768，缩小 57×，且压缩后的 KV state 落盘到 `.coli_kv`，重启可复用。
- **投机解码有硬约束**：MTP head 必须 int8，int4 head 的接受率会崩到 0–4%；draft 与 verify 必须计算同一函数。
- 纯 C 单文件引擎（`c/glm.c`），零外部依赖，OpenMP 多核，CUDA 可选、Metal 实验性。质量上用 teacher-forcing 32/32 与 transformers oracle 做到 token 级一致。

**取舍与局限**：吞吐差异极大——6× RTX 5090 全常驻可达 5.8–6.8 tok/s（TTFT ≈ 13 s），128 GB 纯 CPU 桌面约 1.8 tok/s（warm），单卡 5070 Ti 为 1.07 tok/s，而 25 GB 冷启动基线只有 0.05–0.1 tok/s。也就是说「25GB 能跑」是可用性声明而非性能声明。`O_DIRECT` 收益依盘而定，QLC / 无 DRAM / 虚拟化磁盘可能中性甚至负收益；投机解码是否划算取决于 cache 温度，作者直接建议不划算时 `DRAFT=0`。目前仅支持 GLM-5.2 与 OLMoE，Kimi K2 / Qwen3 MoE / MiniMax 在 roadmap 上。

**可借鉴**：一是设计原则——**默认策略绝不为了速度悄悄改精度或 router 语义**，宁可慢；快慢是资源函数，正确性是不变量。二是「路由可预测性」这个可量化指标，任何稀疏激活系统都可以先测这个数再决定要不要做预取。

## 2. [xai-org/grok-build](https://github.com/xai-org/grok-build) — 22,759 star · 创建于 2026-07-14 · Rust · Apache-2.0

**解决的问题**：coding agent 的价值越来越不在模型本身，而在 harness——上下文如何组织、工具如何授权、长任务如何 checkpoint、TUI 如何在滚动区里稳定渲染流式输出。xAI 把自家 `grok` CLI 的完整实现开了出来，等于把一份生产级 harness 参考实现摆上桌面。

**技术架构**：多 crate 分层，边界划得很清楚：`xai-grok-pager-bin` 是 composition root（产出 `xai-grok-pager` 二进制，发行版里叫 `grok`）；`xai-grok-pager` 只负责 TUI（scrollback、prompt、modal、渲染）；`xai-grok-shell` 是 agent runtime，提供 leader / stdio / headless 三个入口；`xai-grok-tools` 是终端、文件编辑、搜索等工具实现；`xai-grok-workspace` 抽象宿主文件系统、VCS、执行与 checkpoint；`xai-grok-config` 管配置；MCP、markdown、sandboxing 作为叶子 crate 共享。三种运行形态：交互式 TUI、headless（脚本 / CI）、以及通过 **ACP（Agent Client Protocol）** 被其他编辑器嵌入。

**关键实现**：

- **runtime 与 UI 解耦到 crate 级**：同一个 agent runtime 换入口即可从 TUI 变成 CI 任务或被宿主嵌入，这是「一份 agent 三种形态」最省事的做法。
- **扩展面分四层**：MCP server 接外部工具、skills 装领域知识、plugins 加能力、hooks 挂生命周期。四者职责不重叠，比把所有扩展都塞进「插件」要清晰。
- **workspace 层承载 checkpoint 与 VCS**：把「回滚一次 agent 编辑」变成 workspace 的能力而非工具的副作用，长任务失败恢复的语义就统一了。
- 工具实现有部分移植自 OpenAI Codex 与 SST OpenCode（见 `THIRD-PARTY-NOTICES`），交叉阅读能直接看出几家 harness 的收敛点。

**取舍与局限**：**不接受外部贡献**（`CONTRIBUTING.md` 明确说明），本质是「可读可 fork 但不共建」；根 `Cargo.toml` 是生成的，只能改各 crate 的 manifest；Windows 构建为 best-effort 且未从该 tree 测试过，主力平台是 macOS 与 Linux。README 不含 agent loop 伪码与任何性能基准，模型后端细节要翻 `docs.x.ai/build/overview`。构建需要固定版本 Rust 加 DotSlash 管理 protoc 等工具，上手门槛不低。

**可借鉴**：crate 边界即架构文档。想自研 agent CLI 的话，直接照抄这套切分（bin / ui / runtime / tools / workspace / config + 叶子共享 crate）比自己摸索快得多；`sandboxing` 与 `mcp` 独立成 crate 也说明这两块该被当作基础设施而非某个工具的内部逻辑。

## 3. [andrewyng/openworker](https://github.com/andrewyng/openworker) — 6,725 star · 创建于 2026-07-20 · Python · MIT

**解决的问题**：助手类产品普遍停在「给建议」，真正的执行还得人手动做。openworker 的定位是产出**成品**（文档、表格、日历变更、消息），并且把凭据和状态全留在本机。Andrew Ng 出品，7 天累计 6.7k star。

**技术架构**：三层。桌面层是 Tauri（Rust 外壳）+ React UI，负责监督本地 server 并挂一个 Rust 写的 STT sidecar 处理语音输入；中间是 Python agent server（默认 8765 端口，可独立运行），实现 agentic loop、任务分解、工具编排与 memory；底层是 25+ 连接器（GitHub、Slack、Jira、Notion、Outlook、Gmail 等）加终端 / 文件访问，并支持 MCP 扩展。控制流是四步：意图接收 → 分解为子步骤 → **在有后果的动作前插审批门**（发送、日历变更、shell 命令）→ 交付成品而非 todo list。语言占比 Python 58.2% / TypeScript 32.9% / Rust 1.7%。

**关键实现**：

- **模型层走统一抽象**：底座是同作者的 `aisuite`，OpenAI / Anthropic / Gemini / DeepSeek / Qwen / Ollama 一套接口切换，凭据由用户自带（BYOK）。想做 provider 无关的 agent，这条依赖值得单独看。
- **数据边界**：凭据、对话历史、agent 状态全部加密存本地，只有 OAuth broker 走外部——把「本地优先」落到了具体的哪一条流量出网。
- **无人值守用 approval inbox 兜底**：定时任务（morning brief、周报、频道监控）在无人时把待审批动作堆进收件箱而不是自行放行，同时保留完整 transcript。Slack 里 `@OpenWorker` 会在桌面开 session、结果回到 thread。
- 每个集成可单独开关，权限粒度到工具级。

**取舍与局限**：仍是 beta，Windows 代码签名在做；审批门是设计核心，也直接意味着**做不了完全自主的无人值守**——这是安全换自主性的明确取舍。除 Ollama 外依赖外部 provider，本地优先并不等于本地推理。三语言栈（Python 3.10+ / Node 20+ / Rust）让自建门槛偏高，桌面分发与自动更新逻辑都得自己维护。

**可借鉴**：「approval gate + approval inbox」这一对组合，是当前把 agent 接入真实副作用（发邮件、改日历、跑 shell）最实用的范式：在线时同步确认，离线时降级为异步待办，而不是在两者间二选一。做企业内 agent 的话这套语义可以直接拿走。
